# الأنظمة الموزعة (Microservices) مقابل النواة الواحدة (Monolith): متى وكيف تختار؟

في عالم هندسة البرمجيات، تتكرر موجات من التوجهات التقنية التي تُصوَّر أحياناً كحلول سحرية لجميع المشاكل. كان التحول إلى الخدمات المصغرة (Microservices) أحد أبرز هذه التوجهات. ومع ذلك، اكتشفت العديد من الشركات أن استبدال نظام أحادي بسيط (Monolith) بشبكة معقدة من الخدمات الموزعة جلب تكلفة تشغيلية باهظة دون تحقيق الفائدة المرجوة.

> **قاعدة مارتن فاولر الأولى في الخدمات المصغرة:** "لا تبدأ أبداً ببناء نظام خدمات مصغرة من الصفر؛ ابدأ بنواة واحدة متماسكة، وتعلم حدود النطاقات (Domain Boundaries)، ثم قم بالتقسيم تدريجياً إذا اقتضت الضرورة فقط."

---

## 1. مقارنة شاملة بين الأنماط المعمارية

| البُعد الهندسي | النواة الواحدة (Monolith) | النواة المنظمة (Modular Monolith) | الخدمات المصغرة (Microservices) |
| :--- | :--- | :--- | :--- |
| **سهولة التطوير الأولي** | سريعة جداً وبسيطة | ممتازة ومنظمة | تتطلب إعدادات بنية تحتية ثقيلة |
| **الاتساق وقواعد البيانات** | معاملات ACID فورية | معاملات ACID محلية | اتساق نهائي (Eventual Consistency) |
| **التعقيد التشغيلي** | خادم واحد أو حاوية مكررة | خادم أو حاوية مكررة | إدارة شبكات، DNS، وتتبع موزع |
| **عزل الأعطال** | خطأ غير معالج قد يعطل التطبيق | خطأ قد يعطل التطبيق ما لم يُعزل | عزل طبيعي؛ عطل خدمة لا يوقف البقية |
| **استقلالية الفرق البرمجية** | تضارب محتمل عند كثرة المطورين | حدود واضحة مع إمكانية التنسيق | استقلالية كاملة لكل فريق |
| **التكلفة المالية للبنية** | منخفضة جداً | منخفضة | مرتفعة (خوادم متعددة، سجلات، شبكات) |

---

## 2. المخطط المعماري: أين تكمن الفروقات الحقيقية؟

### أ. النواة الواحدة المنظمة (Modular Monolith)
قاعدة بيانات واحدة، مستودع كود واحد، لكن الوحدات الوظيفية مفصولة داخلياً بصرامة:

```
┌─────────────────────────────────────────────────────────┐
│                    Modular Monolith                     │
│                                                         │
│   ┌───────────────┐  ┌───────────────┐  ┌───────────┐   │
│   │ Order Module  │  │ User Module   │  │ Payment   │   │
│   │ (In-Process)  │  │ (In-Process)  │  │ Module    │   │
│   └───────┬───────┘  └───────┬───────┘  └─────┬─────┘   │
│           │                  │                │         │
│           ▼                  ▼                ▼         │
│               [ Single Shared Database ]                │
└─────────────────────────────────────────────────────────┘
```

### ب. الخدمات المصغرة (Microservices)
خدمات مستقلة تماماً، لكل منها قاعدة بياناتها الخاصة، وتتواصل عبر شبكة (gRPC / REST / Kafka):

```
 ┌───────────────┐      ┌───────────────┐      ┌───────────────┐
 │ Order Service │      │ User Service  │      │Payment Service│
 └───────┬───────┘      └───────┬───────┘      └───────┬───────┘
         │                      │                      │
         ▼                      ▼                      ▼
  [ Orders DB ]           [ Users DB ]           [ Payments DB ]
         │                      ▲                      ▲
         └──────── Event Bus ───┴──────────────────────┘
                   (Kafka / RabbitMQ)
```

## 3. شجرة اتخاذ القرار المعماري (Architectural Decision Tree)

لتحديد المعمارية الملائمة لمشروعك، أجب عن الأسئلة التالية:

```
هل عدد المطورين في الفريق أقل من 20 مطوراً؟
   ├── نعم ──> اختر [ Modular Monolith ] ووفر وقتك ومواردك لبناء المنتج.
   └── لا
        └── هل توجد أجزاء في النظام تحتاج موارد حاسوبية فائقة ومتفاوتة جداً؟
             ├── نعم ──> افصل تلك الأجزاء فقط كخدمات مستقلة (Hybrid Architecture).
             └── لا  ──> ابقَ مع [ Modular Monolith ] وحسّن الكفاءة الداخلية.
```

## 4. معضلات الخدمات المصغرة التي يجب الاستعداد لها

إذا قررت الانتقال إلى الخدمات المصغرة، فستحتاج إلى حل المشكلات التالية عبر أنماط معمارية متخصصة:

1. **المعاملات الموزعة (Distributed Transactions):** لا يمكنك استخدام `BEGIN TRANSACTION` عبر خدمتين مختلفتين؛ ستحتاج لتطبيق **نمط Saga** للتعامل مع التراجع في حال الفشل.
2. **اتساق البيانات:** استخدام نمط **Transactional Outbox** لضمان إرسال الرسائل إلى Message Broker دون فقدان.
3. **المراقبة والتتبع (Distributed Tracing):** استخدام أدوات مثل OpenTelemetry و Jaeger لمعرفة مسار الطلب عبر عشرات الخدمات عند حدوث خطأ أو بطء.

## 5. الأسئلة الشائعة (FAQ)

### س: هل بناء Monolith يعني أن الكود سيكون سيئاً وفوضوياً؟
**ج:** إطلاقاً! الفوضى ناتجة عن غياب الانضباط الهندسي. يمكنك بناء Modular Monolith غاية في النظافة والانضباط يتيح لك الفصل المستقبلي لأي خدمة بسلاسة بالغة متى ما تطلبت الحاجة ذلك.

### س: متى تكون الخدمات المصغرة ضرورة لا مفر منها؟
**ج:** عندما تكبر المؤسسة إلى مئات المطورين المقسمين إلى فرق مستقلة وظيفياً، أو عندما تتطلب بعض الأجزاء معايير أمان خاصة (مثل خدمات الدفع PCI-DSS) أو تقنيات تشغيلية مختلفة كلياً.

> **الخلاصة:** المعمارية الأفضل ليست الأكثر تعقيداً ولا الأكثر حداثة، بل هي التي تحل مشاكل العمل الحالية بأقل قدر ممكن من التعقيد والتكلفة الإضافية.
