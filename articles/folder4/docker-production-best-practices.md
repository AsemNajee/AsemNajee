# أفضل ممارسات Docker للإنتاج: تقليص الحجم وتأمين الحاويات

يُعد بناء صور Docker خفيفة وآمنة من أهم متطلبات نشر التطبيقات في بيئات الإنتاج الحديثة (Production Environments). الصور الكبيرة لا تستهلك مساحات تخزين ونطاق ترددي (Bandwidth) فحسب، بل تحتوي في العادة على حزم وأدوات زائدة تزيد من مساحة الهجوم وسطح الثغرات الأمنية (Attack Surface).

> **قاعدة أمنية حاسمة:** كل حزمة أو أداة لا يحتاجها تطبيقك أثناء التشغيل (مثل مترجمات `gcc` أو أدوات إدارة الحزم `apt`) هي ثغرة أمنية محتملة لا يجب أن تتواجد داخل صورة الإنتاج.

---

## 1. مقارنة أحجام الصور الأساسية (Base Images)

| الصورة الأساسية | الحجم التقريبي | الميزات | بيئة الاستخدام المثالية |
| :--- | :---: | :--- | :--- |
| `ubuntu:latest` | ~78 MB | مألوفة، متوافقة مع كل الحزم | التطوير المحلي والاختبارات الشاملة |
| `debian:bookworm-slim` | ~30 MB | متوافقة مع glibc، مستقرة جداً | تطبيقات C++ و Node و Python المعقدة |
| `alpine:latest` | ~7 MB | بالغة الصغر، خفيفة وسريعة | الخدمات المصغرة، مجمعة مسبقاً (musl) |
| `gcr.io/distroless/static` | ~2 MB | بدون شل أو مديري حزم، أمان فائق | خدمات Go و Rust والمخرجات الثابتة |

## 2. النمط الذهبي: البناء متعدد المراحل (Multi-Stage Builds)

باستخدام Multi-Stage Builds، نقوم بفصل مرحلة الترجمة والتجميع (Build Stage) المحتوية على الأدوات الثقيلة، عن مرحلة التشغيل النهائية (Runtime Stage) التي لا تحتوي سوى على الملف التنفيذي فقط.

### مثال متكامل لتطبيق Go أو Spring Boot:

```dockerfile
# -------------------------------------------------------------
# المرحلة الأولى: البناء والتجميع (Builder Stage)
# -------------------------------------------------------------
FROM golang:1.22-alpine AS builder

WORKDIR /app

# 1. نسخ الاعتماديات أولاً للاستفادة القصوى من Docker Cache
COPY go.mod go.sum ./
RUN go mod download

# 2. نسخ الكود وتجميعه
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o myapp .

# -------------------------------------------------------------
# المرحلة الثانية: التشغيل الإنتاجي (Production Stage)
# -------------------------------------------------------------
FROM alpine:3.19

# إنشاء مستخدم محدود الصلاحيات للأمان (Non-root user)
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /home/appuser

# نسخ الملف التنفيذي المترجم فقط من مرحلة البناء
COPY --from=builder --chown=appuser:appgroup /app/myapp .

# تشغيل الحاوية تحت المستخدم العادي وليس root
USER appuser

EXPOSE 8080

ENTRYPOINT ["./myapp"]
```

## 3. التدقيق الأمني وفحص الثغرات (Vulnerability Scanning)

لا ترفع صورتك أبداً إلى السجل (Docker Registry) قبل فحصها بحثاً عن الثغرات المعروفة (CVEs):

```bash
# 1. الفحص الفوري باستخدام Trivy
trivy image myapp:latest

# 2. الفحص باستخدام Docker Scout المدمج
docker scout cves myapp:latest

# 3. معرفة ما يحتويه كل مسار في الصورة وتحليل الطبقات
docker history myapp:latest
```

## 4. قائمة ممارسات الإنتاج الإلزامية

- [x] **عدم استخدام الوسم `:latest` أبداً في الإنتاج:** حدد إصداراً ثابتاً مثل `node:20.11-alpine` لضمان استقرار البناء.
- [x] **تشغيل الحاوية بمستخدم غير root:** استخدم تعليمة `USER` دائماً لمنع اختراق النظام المضيف في حال حدوث ثغرة.
- [x] **ترتيب أوامر Dockerfile بعناية:** ضع الأوامر الأقل تغييراً (مثل تثبيت الحزم الأساسية) في البداية للاستفادة من الـ Cache.
- [x] **استخدام ملف `.dockerignore`:** لمنع تسريب ملفات `.git` ومفاتيح البيئة `.env` والملفات المؤقتة إلى الصورة.
- [ ] **تشغيل الحاوية بنظام ملفات للقراءة فقط:** استخدام خيار `--read-only` في بيئة التشغيل.

> **النتيجة:** باتباع هذه الخطوات، تتقلص صور الحاويات من مئات الميغابايتات إلى بضعة ميغابايتات، وتنخفض احتمالية التعرض للاختراق بنسبة تفوق 80%، وتتسارع عملية النشر والتوسع عبر السحابة بشكل مذهل.
